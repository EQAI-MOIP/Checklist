# 진단기준·진단규칙 이식 및 출처

## 이 앱에서 제공하는 점검 기준

이 앱은 심사관이 자신의 출원 사건을 원문과 대조하여 점검하고 기록하도록 만든 수동 체크리스트입니다. 체크 질문·안내문·자료 입력 예시는 아래 두 저장소의 내용을 자기점검 흐름으로 재구성한 편집 내용입니다. 공식 진단기준의 전체 세부 매뉴얼을 그대로 전재한 것으로 표시하지 않습니다.

- 체크리스트: **8개 관점, 66개 항목**
- 규칙 원문: **OA 17개, RD 6개, RC 7개**
- 진단코드 사전: 저장소에 수록된 **84개 코드의 첫 문장과 적용 안내**
- 확인일: **2026-11-23**
- 실행 중 규칙 다운로드, 외부 API, 외부 라이브러리는 사용하지 않습니다.

체크리스트의 완료 비율은 자기점검 진행 정도입니다. EQAI_sheet의 공식 점수나 심사품질 등급으로 해석하지 않습니다. 체크 완료는 특허성 보증 또는 하자가 없다는 자동 판정도 아닙니다.

| 선택한 점검 단계 | 표시할 항목 수 |
|---|---:|
| 의견제출통지 검토 (`notice`) | 51 |
| 최후통지 검토 (`final`) | 52 |
| 거절결정 검토 (`rejection`) | 59 |
| 등록 검토 (`registration`) | 59 |

단계별 표시 수는 데이터의 적용 범위에 따른 값입니다. 실제 해당하지 않는 개별 사항은 사유를 기록하여 제외합니다. 자료 미확보나 아직 읽지 않았다는 사정은 비적용 사유가 아닙니다.

## 답변과 기록 원칙

- **미확인:** 아직 점검하지 않았거나 판단에 필요한 확인이 남아 있습니다.
- **확인완료:** 필요한 원문을 대조하고 해당 질문을 확인했습니다. 무엇을 검토했는지 근거를 남깁니다.
- **보완필요:** 문제, 자료 부족, 추가 확인 또는 수정 조치가 남아 있습니다. 필요한 자료·할 일·완료 조건을 기록합니다.
- **해당없음:** 그 사건·문서에 해당 규칙의 대상이 없습니다. 구체적인 비적용 사유를 기록합니다.

근거에는 가능하면 문서 종류·식별자·일자, 쪽수·문단·도면, 대상 청구항, 적용 법조항, 원문 일부, 실제 확인 결과를 함께 적습니다. 인용문헌 대조는 통지서 위치와 인용문헌 원문 위치를 양쪽 모두 남깁니다.

## 보존한 핵심 조건

### 공식 코드와 검사 절차의 구별

OA/RD/RC는 검사 절차 ID입니다. 네 자리 숫자는 진단유형입니다. 코드 목록에 존재한다는 이유만으로 실체 판단이 맞는 것은 아닙니다. `11xx` 코드는 원문에 없어 만들지 않았습니다.

### 결정 경과와 영향

`xx12` 계열이나 `0717`, `0812` 등은 각 원문 조건을 읽어야 합니다. 통지 단계의 오지적, 해당 이유로 거절결정한 경우, 다른 정당한 이유가 남는 경우를 구분합니다. `1311`은 출원인 주장·보정 검토 누락과 최종결정에 대한 명백한 영향의 근거가 필요합니다. 아직 결정되지 않은 자기 사건에서 결정 전제 코드를 확정해서는 안 됩니다.

### 최후통지와 최초부터 존재한 이유

최후통지는 OA-15를 적용하여 보정 전후 전체 청구범위와 이유 발생의 인과관계를 확인합니다. 새 문헌·새 법조항·나중 발견만으로 보정에 따른 발생이라고 하지 않습니다. `1024`와 `1031`은 별개 요건과 예외를 확인하며 자동 중복 집계하지 않습니다.

### 인용발명 실제 대조

문헌번호·식별번호·수치범위·도면을 실제 원문에서 확인합니다. 통지서만으로 명백히 정정되는 단순오기와 원문을 읽어야 정확한 뜻을 알 수 있는 오기를 구분합니다. 원문 미확보 시 오기 의심을 확정된 `1231`로 바꾸지 않습니다.

### 거절결정 비교

결정 이전의 모든 통지를 대조합니다. 의견서가 없더라도 확보한 통지·결정으로 확인 가능한 새 이유·문헌 조합·대상항·내부 모순은 점검합니다. 확인되지 않은 실제 출원인 주장이나 보정 효과만 추정하지 않습니다.

### 등록청구항

최종 유효 청구항 전체를 대상으로 인용관계, 다중 인용 경로, 선행기재, 기능 정합성, 보호범위를 확인합니다. `바람직하게`·`특히` 등은 두 한정의 효력과 실제 해석 장애를 기록하며 `임의로`의 명확한 선택적 구성과 구분합니다. 발명의 설명만의 표현이나 삭제항은 현재 등록청구항 하자로 집계하지 않습니다.

### 우수사례

`1511`, `1521`, `1522`는 우수사례입니다. 일반 코드의 세 번째 숫자만 보고 부적합·주의 하자로 분류하지 않습니다. 데이터에 `kind: "excellent"`, `severity: "우수사례"`를 명시했습니다. 원문 첫 문장에 언급된 공통사항·세부 (1)–(4) 등은 전체 기준 원문을 추가 확인해야 하므로, 이 사본의 첫 문장만으로 충족을 확정하지 않습니다.

## 원문·운영 기준·편집 안내의 구별

- `references/diagnostic-codes.md`: 저장소가 보존한 진단유형 첫 문장과 운영 안내를 그대로 수록합니다.
- `references/office-action-rules.md`, `rejection-decision-rules.md`, `registered-claim-rules.md`: 저장소의 검사 규칙 원문입니다. 일부 사용자 확인 운영 기준과 사례가 포함되어 있으며, 해당 문구를 판결의 직접 판시나 최신 법령으로 바꾸어 설명하지 않습니다.
- `js/rules-data.js`의 질문·standard·guidance·evidenceHint: 이 앱을 위한 편집·재구성입니다.
- 각 항목의 규칙 원문 보기: 예외·보류·코드 조건까지 읽을 수 있도록 원문 전체를 보존합니다.

이 패키지는 법령 최신성이나 적용 시점의 공식 법령을 인터넷에서 자동 확인하지 않습니다. 적용시점이 판단을 좌우하면 업무 환경에서 확보한 해당 시점의 공식 원문과 대조하고 그 결과를 기록합니다.
