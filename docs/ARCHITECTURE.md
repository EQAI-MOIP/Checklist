# 큐리 심사 체크 v1.2.0 구조와 유지보수

## 실행 구조

배포물은 정적 HTML, CSS, 일반 JavaScript와 로컬 WebP입니다. GitHub Pages의 저장소 하위 경로에서 제공하거나 `index.html`을 `file://` 주소로 열어 실행합니다. npm 설치, 빌드, 웹 서버, 서비스 워커, 외부 API가 실행 전제에 포함되지 않습니다.

| 파일 | 역할 |
|---|---|
| `index.html` | 앱 기본 구조, 내비게이션, 다이얼로그·백업 입력·인쇄 영역, CSP |
| `css/app.css` | 공통 화면·반응형·인쇄·동작 줄이기 스타일 |
| `css/public.css` | v1.2.0의 글자 크기·접근성·반응형·저장 안내 화면. 인쇄 CSS에는 영향 없음 |
| `css/guided.css` | 번호 입력, 문서 선택, 한 항목 점검, 큐리 안내와 진행·누락 표시 스타일 |
| `js/rules-data.js` | 8개 관점·66개 항목, 84개 코드 사전, 규칙 원문과 출처 데이터 |
| `js/core.js` | 출원 데이터 모델, 입력 검증, 진행률·차단 조건, JSON 형식, 저장소·병합·CSV 처리 |
| `js/guided-flow.js` | 적용 항목·청구항의 순서, 유효한 재개 위치, 이전·다음·미완료 이동을 계산하는 순수 함수 |
| `js/quri-sprite.js` | 로컬 WebP의 실제 프레임 재생, 가시성·모션 제어 |
| `js/session-lock.js` | Web Locks API 기반 단일 편집 탭. pending·owner·viewer·unsupported·error 상태 관리 |
| `js/app.js` | 화면 렌더링, 해시 경로, 사용자의 편집·내보내기·복원·완료 흐름 |
| `assets/` | 원본 WebP 3개, 프레임 메타데이터, 자산 출처 안내 |
| `references/` | 고정 커밋에서 확보한 기준·규칙 사본. 앱 실행 코드로 불러오지 않음 |
| `tests/core.test.cjs`, `tests/catalog.test.cjs` | 데이터 모델·완료 조건·내장 기준·정적 자원 검사 |
| `tests/guided-flow.test.cjs`, `tests/sprite.test.cjs` | 순서·재개·미완료 탐색과 스프라이트 상태·정지·정리 검사 |
| `tests/app-session.test.cjs` | 모의 DOM에서 실제 UI 스크립트와 이벤트 흐름을 실행하는 회귀 검사. 화면 렌더링 검사가 아님 |
| `tests/browser-flow.test.cjs` | 개발용 선택적 Playwright 검사. 실제 브라우저 실행이 허용되는 환경에서만 명시적으로 실행 |

여섯 JavaScript 파일은 `defer`가 붙은 classic script로 순서대로 로드됩니다. ES module, 동적 import, JSON fetch를 사용하지 않아 로컬 파일에서 모듈 또는 fetch의 출처 제한에 의존하지 않습니다. 화면용 원문도 `QURI_RULES`에 포함되어 있습니다.

전역 진입점은 `QURI_RULES`, `QuriCore`, `QuriFlow`, `QuriSprite`, `QuriSessionLock`이며 UI 코드는 즉시 실행 함수 내부에 상태를 둡니다. `core.js`와 `guided-flow.js`는 개발 검증을 위해 CommonJS로도 읽을 수 있지만, 브라우저 실행에 Node.js가 사용되지는 않습니다.

## v1.2.0 공개 사이트 저장 보호

`#privacy` 화면에서 저장 위치·비전송 범위·접속 기록·백업·동일 출처의 한계를 설명합니다. 브라우저 제목에는 출원번호를 포함하지 않습니다. 일반 입력 폼은 자동완성과 맞춤법 검사를 비활성화하도록 요청하지만 브라우저 확장·운영체제까지 통제하지는 않습니다.

`session-lock.js`는 `quri.examiner.workspace.v1.writer`라는 Web Lock을 잡은 탭만 편집하게 합니다. 읽기 전용 탭은 검색·조회·백업이 가능하며, 편집 탭 종료 후 명시적 재시도로 최신 저장본을 읽고 편집을 시작합니다. `pagehide`에서 저장 후 잠금을 놓고 BFCache 복귀 시 다시 획득합니다. API 오류는 읽기 전용으로 안내하며, API 미지원 환경은 기존 낙관적 충돌 감지로 동작합니다.

모달 대기 중 저장 변경·편집권 상실을 재확인하고, 외부 저장소 삭제는 화면 내용을 유지한 채 백업을 안내합니다. 추가 정보 초안은 작업 JSON과 구별하며 저장 전의 초안은 백업에 포함되지 않습니다. `core.js`는 검증 후 쓰기 직전 원문도 다시 확인하지만, 이 비교만으로 미지원 환경의 동시 쓰기를 원자적으로 보장하지 않습니다.

[입력 내용 저장·전송 검토](PRIVACY_REVIEW.md)와 [공개 운영 안내](GITHUB_PAGES.md)를 함께 유지합니다. `.nojekyll`과 상대 자원 경로를 사용하며 CI는 배포가 아닌 검증만 수행합니다.

## v1.1.0부터 이어지는 화면 흐름

첫 화면의 `#quick-start` 폼은 출원번호 하나를 정규화해 기존 사건을 열거나 새 사건을 만듭니다. 새 사건은 곧바로 문서 종류 선택 화면을 열고 사용자가 `notice`, `final`, `rejection`, `registration` 중 하나를 선택한 뒤 점검을 시작합니다. 모델의 기본값이 `notice`라는 이유만으로 사용자가 문서 종류를 확인한 것으로 처리하지 않습니다.

기본 화면은 질문 하나를 표시하며 현재 관점·전체 순서·확인 방법·필수 누락을 함께 보여 줍니다. `관점 전체 보기`는 선택적 대안입니다. `QuriFlow.sequence()`는 `QuriCore.applicableItems()`의 순서 뒤에 설정된 청구항 번호를 붙입니다. `next()`는 이전·다음 항목을, `nextIncomplete()`는 현재 위치 이후의 미완료 항목을 먼저 찾아 필요할 때 앞쪽으로 돌아갑니다. `resolve()`는 저장한 항목 ID가 현재 유형에 유효하면 사용하고, 유효하지 않으면 첫 미완료 항목 또는 첫 항목을 선택합니다.

필수 기록을 판단하는 로직은 `QuriCore.progress()` 한곳에 유지합니다. 현재 카드의 안내, 진행률, `기록하고 다음`, 최종 누락 목록이 모두 이 함수의 `blockers`를 사용합니다. 누락 안내는 모든 사유를 표시하고 해당 입력란에 초점을 옮깁니다. `나중에 확인`은 현재 답변을 변경하지 않고 이동하므로 완료 조건과 최종 누락 목록에 영향을 주지 않습니다. 항목 이동 후 질문에 초점을 둡니다.

심사관 이름 입력과 기본 이름 설정을 없앴고 검색·CSV·인쇄에서도 이름 필드를 사용하지 않습니다. 기존 v1 백업 호환성을 위해 `examiner`와 `settings.name`은 모델과 JSON에 계속 보관합니다. 추가 정보 수정 시 `examiner`를 덮어쓰지 않습니다.

## 네트워크 의존성과 CSP

HTML의 CSP는 다음 정책을 선언합니다.

```text
default-src 'none';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self';
connect-src 'none';
object-src 'none';
base-uri 'none';
form-action 'none'
```

실행 리소스는 같은 패키지의 파일입니다. 외부 CDN, 웹폰트, JavaScript 프레임워크, 아이콘 패키지, 분석 도구, 원격 이미지, API SDK가 없습니다. UI 아이콘은 직접 작성한 인라인 SVG이고, favicon은 인라인 data URI입니다.

JavaScript의 `fetch`, XMLHttpRequest, WebSocket, EventSource, `sendBeacon`을 통한 통신은 사용하지 않습니다. CSP의 `connect-src 'none'`은 연결 계열 요청을 제한합니다. 소스 자료의 GitHub URL과 원문 안의 법령·사례 URL은 출처 정보이며 앱이 자동으로 접속하지 않습니다. SVG의 `http://www.w3.org/2000/svg` 문자열은 네임스페이스 식별자입니다.

`file://` 출처 해석과 로컬 저장 정책은 브라우저마다 다를 수 있습니다. 기능 수정 시 실제 `file://` 경로를 열어 확인해야 하며, 로컬 HTTP 서버만으로 테스트하면 폴더 실행 조건을 충분히 확인한 것이 아닙니다.

## 규칙 데이터와 적용 범위

앱 화면 버전은 `1.1.0`이며 `QURI_RULES.version`은 `1.0.0`을 유지합니다. 이번 개선에서 내장 66개 질문·적용 유형·핵심 여부·필수 기록 조건은 바꾸지 않았습니다.

`QURI_RULES.categories[].items[]`에 ID, 질문, 기준, 확인 방법, 근거 입력 예, 관련 코드, 원문 참조, 적용 유형, 핵심 여부를 둡니다. 사건의 `type`과 각 항목의 `appliesTo`를 대조하여 현재 적용 항목을 계산합니다.

적용 유형은 `notice`, `final`, `rejection`, `registration`입니다. 현재 내장 데이터에서 적용 항목 수는 각각 51, 52, 59, 59개입니다. 전체 항목 66개 중 적용하지 않는 항목을 화면에서 숨기지만, 그 항목에 이미 작성한 답변은 보관합니다.

질문과 안내는 수동 자기점검용 편집 내용입니다. 진단코드·OA/RD/RC 규칙 원문은 출처와 분리해 보관합니다. `codeRefs`는 참고 후보 연결이며 자동 코드 부여 또는 품질 점수 산출로 해석하지 않습니다. 기준 출처와 문서별 보존 범위는 `RULES_AND_SOURCES.md`를 따릅니다.

기존 답변의 키는 항목 ID이므로 이미 배포한 항목의 ID를 다른 의미로 재사용하지 않아야 합니다. 항목의 의미·완료 조건·적용 범위를 바꾸면 이전 완료 상태와 근거의 적합성을 재점검해야 합니다. 지원하지 않는 백업 버전을 자동 변환하는 범용 마이그레이션은 구현하지 않았습니다.

## 저장 데이터 모델

작업 공간은 `localStorage`의 `quri.examiner.workspace.v1` 키에 JSON 문자열 하나로 보관됩니다. HTML 파일을 수정하거나 파일 시스템에 자동 데이터를 쓰지 않습니다.

| 작업 공간 필드 | 의미 |
|---|---|
| `app` | `quri-examiner-checklist` 고정 식별자 |
| `schemaVersion` | 현재 형식 버전 `1` |
| `revision` | 저장 시 증가시키는 낙관적 충돌 검사 번호 |
| `updatedAt` | 작업 공간 수정 시각 |
| `settings` | 호환성을 위해 보존하는 이전 이름(`name`), 모션 줄이기, 핵심항목 근거 필수 여부 |
| `cases` | 출원별 기록 배열 |

| 출원 필드 | 의미 |
|---|---|
| `id`, `applicationNo` | 내부 ID와 정규화한 13자리 출원번호 |
| `title`, `examiner`, `dueDate`, `type` | 명칭, 호환용 이전 이름(화면에서는 사용하지 않음), 점검 계획일, 점검 유형 |
| `claimCount` | 생성할 청구항별 표의 마지막 번호. 실제 유효 청구항 수와 다를 수 있음 |
| `createdAt`, `updatedAt`, `completedAt` | 등록·수정·완료 시각. 미완료는 `completedAt: null` |
| `archived` | 보관함 여부 |
| `responses` | 항목 ID를 키로 하는 관점별 답변 |
| `claimReviews` | `"1"`~`"200"`을 키로 하는 청구항별 답변 |
| `notes` | 종합 메모 |
| `events` | 주요 변경 이력 |

한 답변은 `status`, `memo`, `evidence`, `claims`, `action`, `resolved`, `updatedAt`을 보관합니다. 상태는 `pending`, `pass`, `issue`, `na`입니다. `resolved`는 보완필요 상태에서만 허용합니다.

출원번호는 `10` 또는 `20`으로 시작하는 숫자 13자리를 정규화합니다. 번호 형식 검사일 뿐 실제 출원의 존재를 조회하거나 번호의 실질적 유효성을 확인하지 않습니다. 동일 작업 공간에서 출원번호와 내부 ID의 중복을 거부합니다.

현재 제한은 출원 2,000건, 청구항별 표 1~200번, 개별 메모·근거·조치 12,000자, 종합 메모 40,000자입니다. 실제 저장 가능량은 브라우저 저장소의 할당량에 따라 더 작습니다. UI가 만드는 주요 이력은 최근 1,000건까지 보존하며 화면과 인쇄 보고서는 최근 50건을 표시합니다. 전체 텍스트 수정 내역을 복원하는 감사 로그는 아닙니다.

### 화면 위치와 문서 선택 대기

재개 위치는 작업 공간 JSON의 새 필드로 추가하지 않고 별도 `localStorage` 키 `quri.examiner.cursor.v1`에 출원 내부 ID별로 보관합니다. 항목 `id`, 화면 `screen`, 보기 방식 `mode`, 문서 선택 여부 `confirmed`를 기록합니다. 이 값은 JSON 백업·전체 교체 데이터에 포함되지 않고, 저장 실패가 점검 기록의 검증·백업을 막지 않습니다. 손상된 위치 정보는 무시하며 현재 작업 공간에 있는 출원만 읽고 보관합니다. 위치 저장은 편의 기능이므로 업무 기록의 저장 상태와 동일한 보장을 제공하지 않습니다.

새 사건을 만들 때 기존 `events` 배열에 `awaiting-type` 이력을 남깁니다. 문서를 선택하면 `type`, 추가 정보를 저장하면 `metadata` 이력을 남깁니다. 선택 대기 이력만 있는 사건은 별도 위치 정보가 없는 JSON 복원에서도 문서 선택 화면으로 돌아갑니다. 새 스키마 필드나 백업 버전을 추가하지 않으면서 미선택을 기본 `notice` 확인으로 오인하지 않게 합니다. 이전 v1 사건처럼 선택 대기 이력이 없는 기록은 저장된 유형을 계속 사용합니다.

완료·보관된 사건을 열 때는 최종확인 화면을 사용합니다. 다른 환경에서 JSON을 불러왔을 때 마지막 화면이 그대로 재현된다고 보장하지 않으며, 현재 유형의 적용 항목과 누락 상태로 재개 위치를 결정합니다.

## 자동 저장과 충돌·손상 처리

일반 텍스트 편집은 약 300ms 뒤 저장하고 주요 상태 변경은 즉시 저장을 시도합니다. 화면 이동·페이지 수명 이벤트에서도 저장을 시도하며, 저장 실패가 있으면 현재 작업을 내보낼 수 있도록 안내합니다.

저장 절차는 기존 JSON을 읽어 검증하고, 예상 `revision`과 비교한 뒤 새 버전을 쓰고 즉시 다시 읽어 일치 여부를 확인하는 방식입니다. 기존 내용이 손상되었거나 예상 버전이 다르면 일반 저장을 중단합니다. 손상된 원문은 명시적 복구 전 덮어쓰지 않고 별도 다운로드할 수 있습니다.

다른 창의 `storage` 이벤트가 발생했을 때 현재 창에 미저장 변경이 있으면 충돌 상태로 바꿉니다. 미저장 변경이 없으면 저장된 최신 내용을 불러옵니다. 사용자는 각 창의 JSON 백업을 보존하고 기준 버전을 다시 불러올 수 있습니다.

이 방식은 비교와 쓰기 전체를 원자적으로 잠그는 트랜잭션이 아닙니다. 두 창이 같은 버전을 읽고 아주 가까운 시점에 저장하는 모든 경합을 막지 못할 수 있습니다. `localStorage.setItem` 한 번의 쓰기와 앱의 여러 단계 검사 절차를 구분해야 합니다. 동시 편집 서버나 다중 사용자 동기화 기능으로 사용하지 말고 한 창에서 작업하는 것이 기본 사용 방식입니다.

저장소 접근 거부·할당량 초과·손상·충돌을 화면에 표시합니다. 현재 메모리 작업은 JSON 내보내기로 보관할 수 있습니다. 저장 오류 상태에서 내보내기까지 하지 않고 창을 닫으면 복구를 보장할 수 없습니다.

초기 저장소 읽기가 실패하고 읽을 수 있는 기존 원문도 없는 경우 UI의 `memoryOnly` 상태로 전환합니다. 이 파일 백업 모드에서는 메모리의 작업 공간을 편집하고 JSON 병합·전체 교체로 불러올 수 있습니다. 자동 저장을 성공한 것처럼 표시하지 않고 종료 전 파일 백업 필요를 알립니다. 읽을 수 있는 원문이 손상된 복구 모드와 이 상태를 구별합니다.

## 완료 조건과 잠금

`QuriCore.progress`가 현재 유형에 적용되는 항목과 지정된 청구항 번호에 대해 완료를 막는 사유를 계산합니다. UI의 모든 누락 안내와 다음 항목 진행 검사, 진행률, 최종확인 목록은 이 계산을 공통으로 사용합니다.

- 미확인 항목은 완료되지 않습니다.
- 핵심항목의 확인완료는 기본 설정에서 근거가 필요합니다.
- 해당없음에는 사유 메모가 필요합니다.
- 관점별 보완필요에는 발견 메모, 근거, 처리 결과와 보완 완료 표시가 필요합니다.
- 청구항별 보완필요에도 발견 메모, 근거, 처리 결과와 보완 완료 표시가 필요합니다. 청구항별 확인완료 상태에서는 근거를 별도 필수 조건으로 요구하지 않지만 기록 칸을 제공합니다.
- 최종 완료 시 직접 확인 체크를 추가로 요구합니다.

진행률은 필수 기록까지 충족한 항목을 기준으로 계산합니다. 목록의 전체 비율에는 청구항별 기록도 포함합니다. 완료 시각이 있고 현재 완료 조건도 충족되어야 완료 상태로 표시합니다. 완료 시각만 있고 이후 조건이 부족해지면 재확인이 필요합니다.

진행 계산의 `issues`와 `unresolved`는 관점별 항목과 청구항별 항목의 합계입니다. 청구항별 부분 합계는 `claimIssues`, `claimUnresolved`에 별도로 둡니다. 같은 실질 쟁점이 두 점검표에 기록되면 각 기록을 따로 세므로 이 값은 고유한 법적 하자의 개수를 의미하지 않습니다.

완료 또는 보관된 사건의 편집은 UI에서 잠급니다. 완료 재개 시 내용은 유지하고 `completedAt`을 비웁니다. 점검 완료는 사용자 기록 상태이며 디지털 서명, 기관 결재, 위변조 방지 인증 기능은 아닙니다.

## 백업·가져오기·출력

JSON 백업 형식은 다음과 같습니다.

```json
{
  "format": "quri-checklist-backup",
  "version": 1,
  "exportedAt": "ISO 8601 timestamp",
  "workspace": { "app": "quri-examiner-checklist", "schemaVersion": 1 }
}
```

위 예시는 외부 래퍼를 설명하는 축약형입니다. 실제 `workspace`에는 앞서 설명한 전체 필수 필드가 들어갑니다. 단일 사건 내보내기는 같은 형식을 쓰되 `cases`에 한 사건을 넣습니다. 작업 공간과 백업 형식 버전은 모두 `1`을 유지하며 v1.0.0의 백업을 읽습니다. 호환용 이름 필드와 문서 선택 대기를 포함한 이력은 JSON에 남지만, 별도 재개 위치 키는 내보내지 않습니다.

가져오기에서 파일 크기 32 MiB, JSON 형식, 앱 식별자, 버전, 필드 종류·길이·범위, 중복 등을 검사합니다. `__proto__`, `constructor`, `prototype` 등 허용되지 않는 키를 거부하며 JSON을 실행 코드로 평가하지 않습니다. UI에서 사용자 문자열과 규칙 원문을 HTML로 넣을 때는 이스케이프하고 원문은 텍스트로 표시합니다.

기본 병합은 현재 작업의 출원번호를 기준으로 중복 사건을 건너뛰고 새 사건만 추가합니다. 답변 단위 병합이나 최신 시각 자동 선택은 하지 않습니다. 기존 설정을 유지합니다. 전체 교체는 사용자 확인 후 가져온 작업으로 바꾸고 먼저 현재 작업의 백업 다운로드를 시작합니다.

브라우저의 Blob과 object URL로 파일 다운로드를 시작합니다. 이 앱은 다운로드 파일의 디스크 저장 완료를 확인할 수 없습니다. 전체 교체·삭제 전에 다운로드가 차단되지 않았는지 사용자 확인이 필요합니다. JSON·CSV는 암호화되지 않습니다.

목록 CSV와 인쇄 보고서는 심사관 이름 필드를 출력하지 않습니다. JSON 백업에서는 이전 이름을 보존합니다.

CSV는 UTF-8 BOM, CRLF, 따옴표 이스케이프를 사용합니다. 스프레드시트에서 수식으로 해석될 수 있는 앞글자에는 작은따옴표를 붙입니다. CSV는 보기와 외부 정리용이며 앱으로 다시 가져오는 형식이 아닙니다.

인쇄 보고서는 같은 페이지의 인쇄 전용 영역을 만들고 브라우저의 인쇄 기능을 호출합니다. 별도의 PDF 라이브러리를 포함하지 않습니다. PDF 파일 생성은 브라우저의 PDF로 저장 기능을 사용합니다.

## 스프라이트와 접근성

v3 원본 WebP는 1254×1254의 4×4 아틀라스이고 각 행을 한 동작의 네 프레임으로 사용합니다. 기본 순서 `0,1,2,3,2,1`을 네이티브 타이머와 CSS 배경 위치로 표시합니다. 큰 정지 포즈용 v2와 검토 상태용 512px 셀 아틀라스도 보존했습니다.

실제 아틀라스 동작은 인사·가리키기·읽기·완료의 네 가지입니다. 논리 상태 `document`와 `compare`는 읽기 행, `evidence`와 `decision`은 가리키기 행, `complete`는 완료 행을 사용합니다. 기존 `welcome`, `review`, `thinking`, `attention`, `success`, `save` API도 유지합니다. `attention`은 정지 포즈이며 현재 보완 안내에서는 실제 프레임이 있는 `decision` 상태를 사용합니다. 여러 논리 상태가 같은 원본 동작을 공유한다는 사실을 `data-quri-state`와 `data-quri-action`으로 구분합니다. 정지 포즈 API에는 기존 v2 포즈와 검토 상태용 포즈를 제공합니다. 이 버전은 새 이미지를 생성하거나 원본 바이트를 변경하지 않았습니다.

시스템 `prefers-reduced-motion`, 앱의 모션 정지 설정, 탭 가시성, `IntersectionObserver`를 반영해 불필요한 재생을 멈춥니다. 점검 화면의 `멈춤/재생` 버튼도 동일한 `reduceMotion` 설정을 변경합니다. 운영체제의 동작 줄이기는 앱의 재생 선택보다 우선합니다. DOM에서 제거된 인스턴스의 타이머와 observer를 정리합니다. 캐릭터에는 접근성 설명이 있으며 업무 상태는 텍스트·버튼과 함께 표시합니다. 애니메이션 자체로 완료나 판단을 추정하지 않습니다.

## 코드 수정과 검증 방향

앱의 HTML·CSS·JavaScript는 압축하거나 난독화하지 않았습니다. 글꼴은 시스템 글꼴을 사용합니다. 기본 UI 수정에는 빌드 과정 없이 해당 파일을 편집하고 `index.html`을 다시 열면 됩니다.

변경 후에는 실제 폴더 실행, 새 출원 등록·새로고침 유지, 네 유형의 적용 항목, 필수 근거·사유, 청구항 수 변경, 완료·재개, JSON 왕복, 중복 병합·전체 교체, 저장 오류·손상·충돌을 확인해야 합니다. 결과를 주장할 때는 코드 검증과 실제 브라우저 검증, Windows 운영 PC 검증을 구분합니다.

규칙을 업데이트할 때는 출처 커밋과 확보일을 갱신하고 원문·편집 내용의 구별을 유지하세요. 기존 항목의 ID·의미·완료 조건 변화가 저장된 사건에 미치는 영향을 확인해야 합니다. 원문에 없는 진단코드를 새로 만들어 자동 부여하지 않습니다.

### 이번 개선의 검증 범위

이번 작업에서는 실행 환경의 제한으로 실제 Chromium 실행과 브라우저의 `file://` 화면 확인이 차단되었습니다. 실제 `file://` 브라우저 통합 동작, 화면 배치·반응형 표시, 다운로드·인쇄 및 Windows 운영 PC 검증은 수행하지 못했습니다. 핵심 모델·내비게이션·스프라이트 제어의 Node 검사, 모의 DOM에서 실제 UI 스크립트의 이벤트 흐름 검사, 구문 검사와 정적 자원·외부 의존성 검사를 수행했습니다. 모의 DOM은 HTML/CSS 렌더링 엔진이 아니며 실제 브라우저를 대신 검증한 것으로 해석하지 않습니다. 최신 실행 결과와 미확인 범위는 `VALIDATION.md`를 따릅니다.

기본 코드 검사는 `node --test tests/*.test.cjs`로 실행합니다. 선택적 브라우저 검사는 기본 실행에서 명시적으로 건너뛰며, 브라우저 실행이 허용된 개발 환경에서 `QURI_BROWSER_TEST=1 node --test tests/browser-flow.test.cjs`로 실행합니다. 이 검사는 기존 Playwright 개발 설치와 Chromium을 사용하고 의존성을 다운로드하지 않습니다. Playwright·Node·테스트 파일은 최종 사용자의 앱 실행 의존성이 아닙니다. 배포 대상 PC에서는 연습용 데이터를 사용하여 최초 실행·저장·새로고침·백업·복원·인쇄 흐름을 확인해야 합니다.
